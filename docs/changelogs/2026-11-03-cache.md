# fix(resource/cache): return errors, verify TLS, add a Redis-only resource

Tracking: alva-ai/mono-meta#1115 (gglib, per-module PR). Stacked on #31.

## 1. Current state

Review (resources C1, C2, C6, C7, C9–C11, C13–C15), proven by tests:

- `Init` called `log.Fatal` when Redis was unreachable, a CA was invalid or
  instrumentation failed, so the process exited inside a library call.
- `IsElastiCache` replaced the TLS settings with `InsecureSkipVerify: true`.
- `Stop` failed on a second call; `OK` was nil before `Init`; a second
  `Init` leaked a client.
- Every consumer got a 50 MB in-memory cache, a pub/sub subscription and
  goroutines, including alva-gateway and stream-relay, which only use the
  Redis client.
- `DCacheConfig.ReadInterval` had no effect. No tests.

## 2. Behavior after this change

- `Init` returns errors and closes what it opened. The ping uses the
  caller's context with a 10 s bound.
- `IsElastiCache` is removed. `TLSServerName` verifies a certificate behind a
  CNAME. No gitops or service sets `REDIS_ISELASTICACHE` (envconfig ignores
  unknown variables, so a stray setting does not fail).
- `Stop` is idempotent; `OK`/`Start` fail before `Init`; a second `Init` is
  an error. Cluster plus Sentinel is rejected.
- New `Redis` resource with only the client. `Cache` keeps its API and
  behavior (client plus dcache).
- `MasterName` is configurable (default `master`). The config is logged at
  Info with the password and CA masked.

Consumer impact: services that treated `Init` as "exits on failure" now get
an error back; alva-backend, alfs and llm-data already check the error from
`resourceManager.Init` and exit themselves (`log.Fatal`/`log.Panic`), so
start-up still fails when Redis is down, now through their own code.

## 3. Decisions

- The split is additive: `Cache` stays for the services that use dcache;
  `Redis` is new. alva-gateway and stream-relay can move to `Redis` when they
  adopt `v0.1.0` (migration note).
- Removing `IsElastiCache` and `ReadInterval` follows G1.
