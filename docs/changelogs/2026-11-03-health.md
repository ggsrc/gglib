# fix(health): readiness follows dependencies, liveness only a stuck safety net (G4)

Tracking: alva-ai/mono-meta#1115 (gglib, per-module PR). Stacked on #31.
Decision G4 = A. **The safety-net rule is decision G13** (open); this PR
implements its recommended option A (`StuckAfter`, default 5 minutes).

## 1. Current state

- Liveness and readiness shared one failure counter fed by database and
  Redis pings; an outage of 20–70 s restarted every pod at once (review
  problem 3).
- No check timeout: a hanging check left the status "healthy" forever.
- Readiness passed before any check had run; `Stop` failed liveness too.
- Unsynchronized state (data races); handlers only registered on a router
  created by `Start`.
- No tests.

## 2. Behavior after this change

- Readiness: ready flag, not stopped, at least one round finished, and at
  most `ReadyCount` consecutive failed rounds. Recovers by itself.
- Liveness: alive flag, and not stuck. Stuck = failing for longer than
  `StuckAfter`, or no finished round for 3 × `ProbeInterval` +
  `ProbeTimeout`.
- Each round runs every check in parallel under `ProbeTimeout`; a check
  still running from an earlier round counts as failed and is not
  restarted.
- 503 for failing probes; logs at the start and end of a failing streak.

Consumer impact: every app-based service, alva-gateway and alva-im-bots get
the new semantics when they adopt v0.1.0. With the deployment templates'
probes (period 10 s, failure threshold 3), a Postgres or Redis outage now
removes pods from traffic without restarting them, and restarts only pods
whose checks are still failing after 5 minutes.

## 3. Decisions

- G4 = A; G13 option A pending confirmation (if B is chosen, the
  fresh-connection probe is added per resource; the readiness changes stay).
- `LiveCount` removed; no deployment sets it.

## 4. Changes
