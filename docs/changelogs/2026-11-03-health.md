# fix(health): readiness follows dependencies, liveness only a stuck safety net (G4)

Tracking: alva-ai/mono-meta#1115 (gglib, per-module PR). Stacked on #31.
Decision G4 = A. The safety-net rule is decision G13 = A, with
`StuckAfter` defaulting to 3 minutes (Yumin, 2026-11-03).

## 1. Current state

- Liveness and readiness shared one failure counter fed by database and
  Redis pings; an outage of 20–70 s restarted every pod at once (review
  problem 3).
- No check timeout: a hanging check left the status "healthy" forever.
- Readiness passed before any check had run; `Stop` failed liveness too.
- Unsynchronized state (data races); handlers only registered on a router
  created by `Start`.
- No tests.

## 2. Behavior after this change

- Readiness: ready flag, not stopped, at least one round finished, and at
  most `ReadyCount` consecutive failed rounds. Recovers by itself.
- Liveness: alive flag, and not stuck. Stuck = failing for longer than
  `StuckAfter`, or no finished round for 3 × `ProbeInterval` +
  `ProbeTimeout`.
- Each round runs every check in parallel under `ProbeTimeout`; a check
  still running from an earlier round counts as failed and is not
  restarted.
- 503 for failing probes; logs at the start and end of a failing streak.

Consumer impact: every app-based service, alva-gateway and alva-im-bots get
the new semantics when they adopt v0.1.0. With the deployment templates'
probes (period 10 s, failure threshold 3), a Postgres or Redis outage now
removes pods from traffic without restarting them, and restarts only pods
whose checks are still failing after 3 minutes (about 3.5 minutes with the
liveness probe's 3 × 10 s).

A short outage needs no restart: pgxpool pings a connection idle for more
than 1 s before handing it out and replaces a broken one, and go-redis drops
broken connections and keeps probing the dial in the background. Readiness
fails within one `ProbeInterval` (5 s) of the outage and passes again within
one interval of the recovery.

Known gap, fixed in the app rework: an instance restarted while the
database is still down exits at start-up (`Init` cannot ping), so Kubernetes
restarts it with a growing back-off of up to 5 minutes. The app rework keeps
the process up and not ready while it retries `Init`, so a restart during an
outage only means "no traffic" until the dependency is back.

## 3. Decisions

- G4 = A; G13 = A, `StuckAfter` 3 minutes instead of the proposed 5 (a
  shorter wait before a truly stuck instance is restarted; a dependency
  outage longer than that restarts each pod once).
- `LiveCount` removed; no deployment sets it.

## 4. Changes

- `health/health.go` rewritten; `health/doc.go`; `health/health_test.go`
  (fake clock; 96.9%). `health/.coverage-floor` 0 → 96.9.

## 5. Verification

- Tests: healthy; not ready before the first round; outage → not ready but
  alive, then recovery; stuck past `StuckAfter` → not alive, then recovery;
  hanging check times out and is not restarted; stopped loop → not alive;
  `Stop` affects readiness only; flags and `ReadyCount`; concurrent
  `AddHooks`; `GoCheck` with context; constructors and `Start`. The stuck
  and hanging-check tests wait for failed rounds in the server's state, not
  for a failing readiness probe, which also fails before the first round:
  under load the fake clock could move before the first round, and the stuck
  test failed about once in 40 runs. Passed 60 runs with `-race`, and 4 × 30
  runs in parallel with `-cpu=1,2`.
- `make tidy-check build vet test lint cover` — all modules pass.
